# Day 7 错误覆盖 — 核心知识点与分析

## 概述

Day 7 的目标是把项目中「隐式的错误处理」变成「显式的用户可见状态」。
在这之前，很多错误只做 `debugPrint` 日志——开发者能看到，用户看不到。
这对一个要上架 App Store 的产品来说是不可接受的。

---

## 一、状态矩阵思维

### 为什么需要状态矩阵

一个页面不是只有「正常」和「出错」两种状态。真正的状态矩阵更细：

| 状态 | 触发条件 | 用户预期 |
|------|---------|------|
| 加载中 | 异步操作进行中 | 看到进度，知道在努力 |
| 加载失败 | 异步操作抛异常 | 看到原因 + 能重试 |
| 空数据 | 操作完成但结果为空 | 看到引导，不误以为卡死 |
| 正常 | 一切正常 | 看到内容 |

**核心原则：每一种可能的状态，UI 都该有对应的渲染分支。** 用户不应该看到「什么都没有发生」的空白页。

### 本项目 Day 7 补齐的状态

```
修复前：
  模型加载失败 → 用户看到 loading 消失但页面空白（_modelError 存了，UI 不渲染）

修复后：
  模型加载失败 → 全屏错误视图：图标 + 说明 + 重试按钮 + 返回按钮
```

## 二、错误状态传递模式

### Provider → Page 的标准链路

```
┌─────────────┐     ┌──────────────┐     ┌───────────┐
│  try/catch   │ →   │  _error 字段  │ →   │  UI 分支   │
│  (engine/   │     │  (Provider)   │     │  (Page)    │
│   repository)│     │               │     │            │
└─────────────┘     └──────────────┘     └───────────┘
                         ↑
                    notifyListeners()
                    触发 Consumer rebuild
```

### ChatProvider 实现要点

```dart
// 1. 存储错误
String? _error;

// 2. 公开 getter
String? get error => _error;

// 3. 清除方法（防止 SnackBar 重复弹出）
void clearError() => _error = null;

// 4. 重试方法（清错 + 重新加载）
Future<void> retryLoadModel() async {
  _modelError = null;
  await loadModel();
}
```

### ChatPage 消费要点

```dart
// 加载失败 → 展示错误视图（替代 loading 页）
if (chatProvider.hasModelError) return _buildModelErrorView(chatProvider);

// 推理失败 → SnackBar 通知（不影响对话继续）
chatProvider.addListener(() {
  if (chatProvider.error != null) {
    showSnackBar(...);
    chatProvider.clearError();  // ⚠️ 及时清除，防止重复触发
  }
});
```

**关键细节**：`clearError()` 的时机很关键。如果在 listener 中不清除，下一次 `notifyListeners()` 会再次触发 SnackBar，造成弹窗风暴。

## 三、SnackBar 防抖

### 问题

用户反复按 Enter 键 → `onSubmitted` 每秒触发 5-10 次 → 每次都调 `showSnackBar()` → SnackBar 堆叠排队，逐一弹出。

### 方案对比

| 方案 | 效果 | 问题 |
|------|------|------|
| `clearSnackBars()` 后 show | 清除队列，只留最新 | 快速连点仍有视觉闪烁 |
| 时间戳 throttle（500ms） | 窗口内只放行一次 | 需要全局状态 |

### 最终选择

全局 throttle——因为 `clearSnackBars()` 只能清队列，但当前正在展示的 SnackBar 仍然在动画中，新 SnackBar 会叠加。500ms 的 throttle 从源头减少无效调用。

```dart
class SnackBarThrottle {
  static int _lastAt = 0;

  static void show(BuildContext context, String message, {int throttleMs = 500}) {
    final now = DateTime.now().millisecondsSinceEpoch;
    if (now - _lastAt < throttleMs) return;  // 窗口内直接吞掉
    _lastAt = now;

    ScaffoldMessenger.of(context)
      ..clearSnackBars()       // 清队列
      ..showSnackBar(SnackBar(content: Text(message)));
  }
}
```

**代价**：全局共享一个时间戳——500ms 内 A 页面的 SnackBar 会阻止 B 页面的 SnackBar。但对于移动端 App，用户在 500ms 内跨页面操作的概率极低，这个 tradeoff 可接受。

## 四、分层规则强制执行

### 违规发现

`insights_page.dart` 直接 import 了 `mindmap/engine/mindmap_service.dart`。

按项目分层规则，page 只能依赖 provider / model / core，不能跨层直接依赖 engine。

### 修复方式

```
修复前：InsightsPage ──→ MindMapService (engine)  ❌
修复后：InsightsPage ──→ InsightProvider ──→ MindMapService (engine)  ✅
```

新增的 `InsightProvider` 是一个**薄封装层**——它不包含任何业务逻辑，只是把 MindMapService 的接口透传出去。它的价值不在功能，在于**架构合规**：

1. Page 不知道 MindMapService 的存在（解耦）
2. 如果 MindMapService 的接口变了，只需改 InsightProvider，Page 不受影响
3. 未来可以在 InsightProvider 中加入状态管理（loading/error/cache），Page 侧的改动最小

### 什么时候该抽 provider

有一个简单判断标准：**如果你在 page 里写了 `new XxxService()` 或者 `import .../engine/...`，就该抽 provider。**

## 五、测试设计

### 测试环境限制

Day 7 的测试遇到了真实的约束：
- `flutter test` 依赖 `flutter_tester` WebSocket，沙箱中不可用
- `dart test` 会因为 `llama_cpp_dart` 的 FFI binding 崩溃（纯 Dart VM 无法加载 .dylib/.so）
- `sqflite` 在测试环境没有真实数据库

### 应对策略

| 约束 | 策略 |
|------|------|
| llama_cpp_dart FFI | 测同步 API（getter/方法存在性），不触发异步加载 |
| sqflite 不可用 | 用 `TestConversationProvider` 子类覆盖异步方法 |
| 沙箱限制 | 用 `dart analyze` 验证代码逻辑正确性 |

### 写了什么测试

```
chat_page_error_test.dart       → ChatProvider 错误 API 初始状态 + 方法存在性
history_page_error_test.dart    → HistoryPage 三态视图（loading/error/empty）
topic_selection_validation_test → 空话题/有效话题 SnackBar 行为
```

**核心教训**：端侧 AI 项目测试的难点不在逻辑，在**原生依赖不可用**。解决方案是分层测：
1. 纯 Dart 逻辑 → 单元测试（最快、最稳）
2. Widget 渲染 → 用 mock provider 隔离原生依赖
3. 端到端 → 在真机/模拟器上跑 integration test

## 六、边界 case 防御

### 空话题校验

用户可能输入纯空格或直接按 Enter。如果跳转到 ChatPage 时 topic 为空字符串：
- 欢迎消息匹配不到预设话题，会走到兜底：「你想和我聊聊什么话题？让我们从头开始」
- 体验上不差，但语义上不准确——用户本来就没设置话题

所以 Day 7 加了客户端校验：`trim().isEmpty` → SnackBar + 不跳转。

### 超长回答限制

端侧推理的 Context 窗口只有 4096 tokens。如果用户输入 5000 字的回答——加上对话历史——大概率触发 context overflow。

Day 7 的双重限制：
1. `TextField.maxLength = 3000`（UI 层面，用户几乎输不到）
2. `onSend` 回调中二次校验（防御性编程，belt-and-suspenders）

## 七、关键收获

| 序号 | 知识点 | 一句话 |
|:--:|------|------|
| 1 | 状态矩阵 | 每一种 async 状态都要有对应的 UI 分支 |
| 2 | Provider 错误模式 | try/catch → `_error` 字段 → `notifyListeners()` → Page 消费 |
| 3 | `clearError()` 时机 | listener 中立即清除，防止 `notifyListeners()` 触发 SnackBar 风暴 |
| 4 | SnackBar 防抖 | 全局 throttle 比 `clearSnackBars` 更彻底，500ms 的 tradeoff 可接受 |
| 5 | 分层价值 | provider 薄封装的成本是 40 行代码，换来的收益是 engine 层可独立演进 |
| 6 | 测试策略 | 端侧 AI 项目要分层测：Dart 逻辑 → mock provider → 真机 e2e |
| 7 | 边界防御 | belt-and-suspenders：UI 限制 + 逻辑校验，两层比一层安全 |
